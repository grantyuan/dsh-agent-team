# Host authority

English | [中文](host-authority.zh.md)

Team is one collaboration domain per DSH home. Its append-only operation ledger is durable authority for Member, Workspace, Channel, Message, independent Thread aggregates, optional Task overlays, Claim, Thread Attention, Inbox, pending Member interrupts, and Activity facts.

When changing a Host capability, read package source/tests first and then the matching Harness contract. [`harness-navigation.md`](../harness-navigation.md) maps the route to `deepseek-harness/docs/subsystems/` and source packages.

## Ledger authority and commits
- Mutations enter Host authority and commit one durable operation. Projections, Inbox, tools, commands, Remote responses, and UI derive from committed operations; Client code never interprets ledger records or creates parallel authority.
- One writer per ledger file, enforced at the Team layer (`ledger-fence.ts`): sequence numbers come from a Host's in-memory replay and the Harness storage domain declares cross-process write coordination out of scope, so two live ledgers over one medium interleave and fork the operation chain — detected only fail-closed at the next replay.
- A Host whose composition config names the shared SQLite ledger directory (`ledgerDirectory`, shipped on the Host row beside the SQLite route) claims a lock in it at mount — last claim wins, so a legitimate remount is never blocked by the instance it replaces.
- Every earlier holder — a same-process patch-reload survivor or another host process — fails its next ledger call, latches itself superseded, and commits nothing further. A Host never given the directory (a memory-backed test harness) is unfenced and touches nothing in the DSH home; the fence narrows the double-writer window to one in-flight commit, where full closure would need storage-layer compare-and-swap the Harness does not offer.

## Lifecycle and notifications
- Agent lifecycle, JSON/SQLite replay, authorization, idempotency, and revision checks stay on Host. Durable unread changes may produce one bounded coalesced Agent context notification through the public safe boundary: direct mentions carry their Message and source, Task/Claim Activities carry a concise transition, and ordinary unread carries only a body-free Thread-first route. Promotion is a Task activity and reaches followers through Activity markers. Notifications are not a second authority and do not promise exactly-once model processing.
- Member supervision (`supervisor.ts`) is the automatic last resort behind `recovery.ts`. One tick every ten minutes — armed only after the startup Member restore settled, so cold Sessions never read as stops — watches every enabled Member. A tick advances the Host's open coercion chains first (retrying a reset that never committed, then handing over a Member the reset did not heal) and only then runs the bring-up pass, so an opened chain cannot stall into an endless stream of continue nudges.
- A Member reads settling while its Agent is live and a turn may move (a live-and-idle Member with open Claims waits by design and is never interrupted), and stopped when it is not active, carries an error presence, or has been running with no durable session event for thirty minutes. A stopped Member the chain does not yet own gets one bring-up attempt per pass, up to three; one the chain owns is left to the chain, since a nudge only keeps it running past the boundary the chain's step waits on.
- Supervision never classifies a failure: what opens the coercion chain is the plain failure streak — three `agent/error` turns with no clean turn between them, or three failures inside a twenty-minute rolling window. A context that no longer fits its route is just one more failing turn: the provider's refusal surfaces, the streak counts it, and the chain follows without any context-specific fast lane.
- The chain's first step is the Host's own reset: the same fresh-context reset the Human menu performs, privately noticing only the reset Member, with nothing broadcast to any Channel. The archive-and-replace handover below is the last resort, advancing on a later tick only while the Member still reads abnormal. Reading healthy again closes the chain and re-arms the gentle bring-up.
- Every completed model round passes the response-shape guard (`response-guard.ts`): a round that ends the turn with no tool call and no visible text — or whose text does not end with the `任务结束` completion marker (trailing punctuation or decoration after the marker is still accepted) — is a faulty round, and the Host delivers one `continue` notice, steering a mid-flight turn or opening the next one. At most three consecutive nudges are spent before standing down; any healthy round (a tool call or a marker ending) resets the episode. The notice stays a pure reminder in the context projection.
- The guard also owns the stop boundary: a turn that ends `completed` in the faulty shape — even after the in-loop nudge budget stood down — earns one stop-boundary reminder under a per-Member cooldown, and that reminder re-arms the nudge budget for the round it opens. An interrupted turn, a user abort, or an error stop is a Human or Host event, not a model fault — the stop lane stays quiet and waits for the next round.
- Activation tail-scans a persisted Member's stored Session log and pays the stop reminder to a recent faulty stop that never got one (within a six-hour window, with no pending direct delivery owed to its Inbox), instead of leaving a Member that was stopped mid-work silently idle.
- Replacement runs as ordinary Host lifecycle inside one serialized step: the failed Member goes through the same `archiveMember` (its Claims release with public `claims_released` Activities), and a same-role generation joins under Human authority — handle takes the next free `-N` generation of the role, the mutable role facts carry over, private memory (`memory.md` and `notes/`, deliberately not `skills/`) is copied in before the replacement's first activation, and the predecessor's Channel participation is re-granted.
- The replacement inherits its predecessor's configuration verbatim — the same `presetId`, `description`, `model`, `capabilities`, prompt profile, `contextStartPolicy`, `contextWindow`, and `leader` flag — so its effective settings match the Member it succeeds instead of silently reverting to defaults. It also records a succession edge (`predecessorMemberId`) naming that predecessor; the edge widens the successor's Session lineage to the predecessor's history (the read lives in Workspace, Session, and storage reuse).
- The continuation watcher (`continuation-watcher.ts`) covers the opposite failure of supervision: every Agent healthy and stopped normally, yet Tasks Agents can still advance remain. One pass a minute — armed by the same restore gate as supervision — starts a quiet hold once every enabled Member reads `available` with such Tasks present; any ledger commit restarts the hold (a Human reading counts), and an Agent working again, a changed Task landscape, or a nudge that has sat unheard for ten minutes re-arms it.
- The watcher's open set stops at `in_review`: a Task whose Claims are done awaits Human acceptance, which is not work to remind stopped Agents about, so a Workspace holding only such Tasks never fires — the Human Task list keeps showing them as open.
- After two quiet minutes the Host posts one nudge as the Human admin into the open work's busiest Channel for the Workspace's designated leader (`member.leader`), listing the open Tasks; the `@` mention wakes the leader through the ordinary Inbox path. A Workspace without an enabled designated leader logs once per episode instead of nudging; a failed delivery logs and retries on a later pass. Counters are process-local, exactly like supervision's.
- The completion liaison (`completion-liaison.ts`) owns the per-Member moment right after the watcher: when a Member stops on the `任务结束` marker and stays idle past a short grace, the Host checks whether it addressed any report to the designated leader since finishing (a Channel message naming them or a DM, read from the ledger tail past the completion) and otherwise wakes the leader with one report-check notice in their Channel.
- When the Workspace designates no enabled Leader, the liaison instead pushes the Workspace's open Tasks to the Member and lets it decide — the push states that declining means opening the final reply with `拒绝继续`.
- The designated Leader's own completed stop earns no forced wake at all: no self-push and no self-check. The Leader reports to the Human by duty, and only a Leader failure summons the machine — through the guard and supervision lanes, never through the liaison.
- A captured refusal at the Member's next marker stop ends Task pushes for the process and relays the Member's own words (bounded) to `@human` in the Channel; a decision to continue notifies nothing. Episodes, decisions, refusals, and cooldown latches are process-local like the watcher's counters, while every notice is an ordinary ledger Message.
- The activation tail-scan opens the episode retroactively too: a Member whose marker-completed stop landed while the Host was down (recent by the same six-hour window, with no pending direct delivery already attending to it) still earns its report check on the first restored pass — a deploy restart never leaves an idle unreported Member silently off-policy. The episode's grace measures from the stop and its TTL from when the liaison learned of it.
- Output truncation escalation (`truncation-escalation.ts`) covers the stop the provider forces: a turn ending at the per-request output-token cap (`max-tokens`) leaves the Member's answer truncated but preserved in its Session, and the guard's bounded in-loop nudges can spend themselves re-running one oversized reply — the Member then simply sits stopped, exactly the case the Web UI offers the Human as "send continue".
- The Host never decides for the Team: for every Workspace the Member holds, one escalation notice posts in the Human admin's voice into the designated leader's (`member.leader`, someone other than the Member) Channel, and the ordinary Inbox path wakes that leader to decide — have the Member resume in smaller chunks (writing output into files or posting part by part so it does not hit the cap again), reassign its unfinished work, or leave it stopped for the Human.
- Escalations latch per (Member, Workspace) for ten minutes: a Member truncating again inside the window is one unresolved situation, not new information; a clean 任务结束 marker stop closes the episode so the next truncation escalates fresh, and a Member with no eligible leader logs once per episode. Latches are process-local and every notice is an ordinary ledger Message; the activation tail-scan deliberately never replays a truncated turn across a restart — a restored Member stays quiet until it moves again.
- The replacement then posts one structured retirement notice as the Human admin into the affected business Channel: a headed block naming the retirement cause, the failed Member's completed work in service, an optional best-effort final-Session recap, and the work its release left unclaimed again. With a designated Workspace leader the notice is addressed to that leader alone; only with no reachable leader does it fall back to every Channel the successor inherited, reaching each live fellow Member under an `@human` ask.
- Every durable result of the handover is a ledger operation, so a crash mid-handover replays as a normal ledger, never as a half-faked Team fact; counters and the watch list stay process-local, re-earning their budget after a restart, mirroring the overflow-rescue budget.

## Projections and the change stream
- Host projections over a Member Session fold incrementally. Context intent and the clock baseline each derive from one Session's own events, and both read through a Session event cursor that keeps the folded value beside the log position it consumed — `context-projection.ts` supplies the fold, `session-event-cursor.ts` the position — so the first read of a log folds it once and every later read folds only the events appended since.

  The cursor assumes the log is append-only and verifies what it can: it remembers the sequence and type of the event it stopped on, so a log whose fork prefix moved, that shrank, or that replaced that event re-folds from the start, and a fork, resume, or rollover therefore costs a cold fold at worst rather than yielding a wrong picture.

  One residual is named in the module rather than papered over: an event replaced in place by another of the same type at the same sequence is invisible to that guard, which is reachable only by violating the append-only contract and which a content-sensitive anchor would not close either, because only the anchor position is re-read while a swap at any earlier folded position would pass the same way. Cold paths that read a whole inspected or foreign log — activation, transitions, timeline, carried-input replay — keep folding in full.

  Each of the two keeps one cursor per Member and replaces it when that Member's Session changes, so the retained fold state is bounded by the roster rather than by the number of generations a Member has lived through.
- `changes()` is a streaming Remote with one optional scope (workspace/channel/thread/presence); an omitted scope observes shared Team projection changes, not presence. Host registers the listener before emitting the current baseline, then emits matching invalidations, retaining only the latest pending version while a consumer pauses. Cancellation or Host disposal closes the subscription. Thread reads and `team/dm-sent` change no shared projection, so neither advances its version nor wakes subscribers.

  Presence uses a process-local epoch; other scopes report the latest shared-projection ledger sequence. Versions are meaningful only within their scope and Host lifetime. Host recomputes Inbox hints only for Members affected by an operation.
- `TeamChangeStream` shares one logical stream per scope within each page through `ctx.remote.$stream()`; Harness owns the shared `/api/remote.mux` WebSocket and connection recovery. Each new baseline, including an unchanged or lower version after reconnection, requests a fresh Host read. This closes the initial-read race and recovers failed reads without a new commit. The last listener leaving disposes that scope; plugin disposal closes all scopes. Carrier failures are reported once until recovery; terminal failures are reported without a Team-owned retry loop.

  Team has no long-poll fallback, cross-page leader election, or single-active-page restriction. Concurrent supplemental reads coalesce notifications and retain a trailing read when another notification arrives during a fetch, rather than suppressing reconnect baselines by an old version. The Human Inbox badge subscribes without a scope, debounces Inbox totals, and also refreshes after local Thread reads. Presence subscriptions update Member availability without waking the Inbox. Notifications are invalidation hints, never a second facts store.

## Session persistence and replay
- The bundle targets DSH `0.2.1-alpha.2` and uses the current DSH Session persistence: the shipped JSONL backend migrates released historical formats itself (v0/v1/v2 → V3 → V4), and old-format Session data needs no manual disposal. Team nevertheless retains a narrow replay normalization for old pre-Message `occurredAt` records, and exactly one record shape still reaches it: the pre-receipt `team/thread-read` snapshot, which froze Message anchors and Thread facts beside the Inbox delta it consumed.

  That is the only Thread-read form that stores an instant at all — the receipt every current read writes carries progress and its Inbox delta only — and it is normalized and validated in place, never rewritten. Do not add Team Session migration, broad compatibility reads, or fallback storage paths.

## Attention and Inbox authority
- Thread Attention is private Member × Thread state. The Host is the only Inbox authority. Session history may retain bounded notification context but never a parallel unread projection.
- Per-commit waking is point-to-point: an operation summons a Member's model only when it names them — an added Direct marker (mention or DM), an added Activity marker on their Task, or their own acting. Unaddressed Thread chatter keeps its unread count in the projection and rides along body-free with the next addressed delivery's summary, so shared-Thread traffic spends no turn per follower. Restore-, resume-, and error-time hint re-derivation is a separate lane that still reads all durable unread state.

## Sessions, policy, and context pressure
- Team-managed Agent sessions use the explicit Team preset and trusted `danger-full-access` policy. An untitled Member session receives its handle as a title; explicit or previous titles win.
- Accepted-Task auto compaction is retired, and the Host does not police context size: the pressure coordinator's only lane is the provider-overflow rescue (see Tools and preset) — one bounded compact-and-retry per open failure chain for a request the provider refused because the context no longer fits its route, re-armed only by a successful request, and never attempted on a lane whose routed proxy owns compression.
- Everything a Member reads on demand — the acceptance advice, the `context_timeline` tool, the checkpoint-return guard — is priced from the live route, never a request decision. Pending/error bookkeeping is process-local; only compactions in a transaction add Session history.
- Supervision's whole progress judgment is the plain failure streak (see Lifecycle and notifications): three consecutive `agent/error` turns with no clean turn between them open the coercion chain's fresh-context reset — identity, pinned settings, and private memory intact — with no context-specific classification or fast lane.

## Private memory, archival, and identity effects
- Private-memory directories under `$DSH_HOME/agent-team/members/` are Host-owned effects of Member identity. Activation ensures the directory, `notes/`, and missing `memory.md`; startup does not prune unknown directories. Explicit removal archives the Session and removes that Member's private directory; unrelated entries remain untouched.

  Both that removal and the activation-time rename of a pre-fix colon directory are confined to the running process's own members root — the recorded `privateMemoryPath` is a durable absolute fact that names a directory in whichever DSH home added the Member, so a process resolving another home refuses to move or delete it (with a warning) instead of taking the Member's real private memory out of its home.
- Member and Channel archival is the reversible third state between suspend and remove. `archiveMember` commits `team/member-archived`, disposes the live session (private memory and the Session log stay on disk), archives the Session from grouping surfaces, and releases the Member's active Claims with public `claims_released` Activities plus Attention/marker cleanup — a hidden Member must not leave Tasks stuck in progress or phantom unread counts.

  `archiveChannel` commits `team/channel-archived` with the same release shape across every owner on the Channel's Threads; Memberships survive both archival forms (hidden state, not departure).

  Archived entities are gone from every Team API surface — projections (view channels/threads/tasks/members, mention candidates, Channel joins, edits), ref resolution (`resolveTaskRefs`/`resolveThreadRefs` skip them so message bodies render plain text), and ref-addressed reads (`readThread`/`threadHistory`/`threadObservations`/`listClaims` reject with an explicit archived error, never an unknown-ref disguise) — while the facts stay complete in the ledger for replay and a future restore; that boundary is the archival-vs-remove divide.

  Removal from archived stays available as the data hygiene path, and there is deliberately no restore entry point this round (mirroring archived dsh sessions). Ledgers written before Channel archival omit `channel.state`; the record schema normalizes it to `active` at load.

## Member capabilities and skills
- Member capabilities (`capabilities` on the Member entity: reserved `tools.allow`, `skills.allow`) are durable intent carried verbatim by every lifecycle operation. Committing performs no known-name validation so old ledgers stay replayable across Harness upgrades; divergence is derived at activation as non-persisted `capabilityWarnings`. `tools.allow` is a deliberate interface reservation (no UI write path) that future Runtime Revision manifest orchestration depends on; do not remove during cleanup.

  Edits follow the absent-clears semantics of `model`; callers that do not manage capabilities must echo the stored value back. The `leader` flag is the one keeps-prior field: absent leaves the designation untouched, so editors that echo it stay idempotent.
- Activation applies `tools.allow` as a scoped restriction on the composed preset surface before preset validation (mount → restrict → validate), force-unioning the ten Team tools over the configured list. Unknown names drop with a warning instead of failing activation; restriction failures surface only as that Member's activation failure.

- Editing a live Member's allow-list or prompt profile answers at the ledger commit and swaps the live surface at a turn boundary in the same Session: idle Members apply inside the edit's own queue body; a running Member's swap is a background scheduled apply (the fresh-start reset / auto-prune seam shape), so neither the response nor the serialized lifecycle queue waits on the turn. A handle dropped by any dispose — even one the queue never saw — bails; the stored facts then land at the next activation, and apply failures are logged, never surfaced.
- Skills are Member-private. The preset carries no shared skill-filesystem row; instead the Host registers one filesystem provider per Member on that agent's exact scope layer (the traceable-service seam, same shape as the tool restriction) scanning exactly two Team-owned roots with default roots excluded: the plugin's bundled read-only core skills (`packages/agent-team/core-skills/`, first — a same-name bundled skill stays stable across upgrades) and the Member's writable `$DSH_HOME/agent-team/members/<memberId>/skills/`.

  A Member catalog therefore starts with the bundled set (the `member-skill-manager` meta skill, which owns all skill craft guidance — the persona itself only states the private-space physical facts); installing is writing into the Member's own directory (directory form `skills/<name>/SKILL.md` with optional references/scripts, or a flat `.md`), there is deliberately no upload Remote, and the filesystem watcher feeds discovery.

  `skills.allow` filters `list()` output through a live selection ref (edits swap the filter and invalidate the catalog at the same turn boundary as tool edits); filtering is a visibility semantic, not a security boundary — both roots stay scanned and watched. Member removal deletes the private directory with its skills; suspend/resume and Host restart restore the identical catalog.

## Member context control
- Members carry three optional overlay fields beside `model` and `capabilities`: `contextStartPolicy` (`continue` | `fresh`), `contextWindow` (an integer of at least 8192 tokens), and a `prompt` profile (`droppedSections`, `customPrompt`, `autoPrune`, `autoExecutePrune`). Commit validation caps `customPrompt` at 8192 UTF-8 bytes and normalizes blank to absent. Every field is consumed: the paragraph becomes the Member's custom prompt section, `droppedSections` filters that Member's assemblies, and the auto-prune pair drives the usage sweep — the mechanics live in Tools and preset.
- Add and edit validate at commit, and the record schema mirrors the same floors — a stored record below them would refuse replay. Edits follow the absent-clears semantics of `model`, and ledgers written before the fields existed replay as plain continue/follow-route Members.
- The window override narrows the pressure budget from the route, never widens it: `routeLimitsForAgent` prices the budget from the smaller of the override and the live route window, so an override beyond the route changes nothing. Members without an override behave exactly as before.
- The `fresh` policy renews a Member's context at new-task assignment only: when the Member claims a task, when a Human atomic start names it among the committed direct mentions, or when a teammate's direct dispatch (a mention whose Inbox wake carries unread direct work) reaches it. A DM is pure session relay: it never passes through this gate and never spends the arm.
- The renewal runs through the serialized lifecycle queue — the same `renewMemberContextNow` operation the Human reset path uses — waiting for the Member's turn boundary and converging running Agents like a member transition.
- The renewal is armed, not fired, by completion: a `completed` stop whose round ended on the completion marker arms the Member (the activation tail-scan arms one whose last persisted stop was a marker ending), and finishing a task never renews on the spot.
- The dispatch gate holds a direct-work wake until the renewal lands — the reset notice and fresh system context precede the task body in the new generation — while wakes without direct work (Thread chatter, Task-activity notices) never spend the arm. A landed renewal re-derives the held wake through the same gate (a landed-renewal pass-through keeps the signature dedupe from swallowing it) and the reset body's exit flushes any still-held delivery, so gating never loses work.
- The dispatch gate decides keep-or-renew only while the Workspace has a designated Team Leader: the Host makes one bounded model call that scores the incoming Message against the Member's recent work — its last five authored Messages plus the content of the Task it most recently claimed — and delivers into the live Session unread when the score clears 60%. With no leader, or when the call fails, times out, finds no history, or scores below the bar, the arm is spent on a renewal. Every decision logs its score.
- Only the dispatch being judged counts: the newest direct work decides, and the unread backlog never joins the comparison — one related Message would otherwise keep every later unrelated task alive.
- The sender may still overrule that judgement: when a committed Message carries `keepContext` (a `team_message` start or reply, or a Human atomic start), the Host records the exemption for those direct markers at that operation sequence before emitting the commit and skips the model call. Both the exemption and the judgement are process-local intent, never ledger facts; the exemption is sequence-bound, so it covers exactly that delivery and the next dispatch is judged again. `team_view` prints each Agent's `contextStartPolicy` on its row so the sender can see who renews before dispatching.
- A give-up releases the arm and degrades the dispatch to the pre-renewal context rather than re-scheduling in a hot loop. If the live handle is swapped while a reset is scheduled — a restart, rollover, or dispose — the body re-binds to the current handle and retries, bounded at five bindings, instead of dropping the scheduled renewal with the old one.
- Finishing work is not an assignment: marking a Claim done or accepting a Task commits no renewal, and the read-time acceptance advice for a `fresh` Member keeps the live context instead of advising a rollover, so the completion summary stays readable in the live log until the next assignment renews it.
- Before committing, the scheduler re-reads the stored policy and state: a policy edited away in the meantime, or a Member no longer disposable to its Agent, skips the renewal. The committed reset privately notices only the Member that its fresh-start Task policy renewed, and `continue` Members never renew through this path.
- The `autoPrune` switch adds a usage sweep at the same task boundaries the fresh policy uses. Like the fresh scheduler it waits for the turn boundary, re-reads the stored switch and state there (an edit or suspension in the meantime skips the sweep), and runs inside the serialized lifecycle queue. The usage fold reads whole session files, so it precedes the queue. Ask mode posts the `@human` inbox notice only.
- The queued sweep body only re-validates cheaply — the re-read Member still opts in, and each folded candidate still names a live, unprotected, tool-mapped section — before asking or committing.
- Full-auto (`autoExecutePrune`, never under a partial usage fold) commits the candidate drops as one echo-complete member update under the Human actor, live-applies them at the settled boundary, and still announces. The usage projection is computed on read, never persisted, and a partial fold (an unreadable archive, a lineage past the walk cap) can only degrade the decision — unreadable history may under-count, so it never drives an automatic drop.
- The window prices recent work, not lifetime idleness: a Member idle past the 14-day bound folds zero usage, so full-auto can sweep every mapped section at that Member's next task start — intended per the window semantics, and every drop stays recoverable in the Prompt dialog.

## Composer attachments (cache, not archive)

Attachments live in the bounded cache `$DSH_HOME/agent-team/attachments/v1/<attachmentId>/`, with a sanitized original name and `meta.json`; they are never ledger bytes or an archive. `putAttachment` enforces a 10 MB file cap and sanitizes names; `getAttachment` serves Client display. Messages record metadata while the stored body contains machine-facing `[attachment] <absolute path>` lines. The Client strips those lines and renders thumbnails/chips.

The Channel and Thread composers accept files both through the "+" picker and by pasting into the draft; a paste that carries files is intercepted and joins the same pending-file chips, while plain-text pastes keep their native insertion.

Garbage collection runs at startup and every 24 hours: referenced uploads older than 72 hours and orphaned uploads older than 24 hours are removed, while metadata remains. Agent-sent absolute paths are validated as absolute non-empty regular files under 10 MB, copied into a fresh immutable cache entry, and rejected atomically if any path fails. A manually pasted absolute path is simply read by the Agent; Host touches nothing it does not own.

## Human profile and version footnote

The Human's display name and avatar reference live in the Team Host row's own Config, in the settings namespace `wowyuarm-agent-team-host` (user layer); avatar bytes live in the persistent `$DSH_HOME/agent-team/human/v1/` store, never in the TTL-bound attachment cache.

The retired `agent-team-human` section is no longer an authority: the rc.1 settings importer carries sections across through a closed built-in mapping, so a third-party section stays behind in the renamed legacy document. A boot that finds the row still pristine — the default name and no avatar — adopts those facts through the same write path the settings page uses, and anything already re-entered wins.

Four typed Remotes serve the settings page: `humanProfile` (name, avatar reference, and version footnote facts) and `putHumanAvatar`/`getHumanAvatar`/`removeHumanAvatar` (images only, 10 MB cap shared with attachments; a removed entry throws and the Client falls back to the initial).

The footnote carries the version of the bundle this Host runs from — read from the installed package's own manifest, so it states what the profile actually installed rather than a string every release must remember to bump — plus the repository link and an update tip naming the newer version once a background check has observed a newer published release. The check asks the public npm `latest` document at most every 12 hours, refreshes in the background so profile reads never wait on the network, settles every failure as "no update known", and stays off while `DSH_AGENT_TEAM_UPDATE_CHECK=0`.

The ledger reads the same profile for `team_view` and @ matching, so a rename reaches every surface at once; `human` stays a permanent alias for the Human and no agent handle may claim the literal, so `@human` keeps delivering across renames while chips render the current display name.
